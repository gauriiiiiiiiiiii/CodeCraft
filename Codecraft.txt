CODECRAFT

TECH STACK
- Frontend: Next.js 15 (App Router), React 18, TypeScript, Tailwind CSS, Framer Motion
- Backend/BaaS: Convex (queries, mutations, HTTP actions)
- Auth: Clerk (frontend UI + Convex identity)
- External services: Judge0 (remote code execution), Svix (webhook verification via Clerk)
- State: Zustand
- Editor: Monaco via @monaco-editor/react

1) PROJECT OVERVIEW
- Problem statement: Developers need a zero-setup way to run code and share snippets, with community interactions (comments and stars) and personal execution history.
- Why this exists: Local runtime setup is heavy; remote execution plus a social layer makes sharing and learning faster.
- Real-world use case: Code interview practice, rapid prototyping, sharing solutions, and discussing code in a community feed.
- Target users: Developers, students, and teams that want instant execution and shareable snippets.

2) SYSTEM DESIGN (HIGH-LEVEL + LOW-LEVEL)

2.1 High-level architecture
- Frontend: Next.js App Router for pages, UI components, and client state.
- Backend: Convex for data storage, queries, mutations, and HTTP actions.
- Auth: Clerk for UI login and user identity, enforced in Convex via ctx.auth.getUserIdentity().
- Execution: Judge0 HTTP API for remote code running.

High-level diagram (text)
- Client (Next.js) -> Clerk (auth UI) -> Convex (queries/mutations)
- Client (Next.js) -> Judge0 (code execution)
- Clerk -> Convex HTTP action (webhook) -> Users table

2.2 Low-level design (key modules)
- Editor state and execution: src/store/useCodeEditorStore.ts
  - Stores language, theme, fontSize, editor ref, output, error, executionResult.
  - Manages localStorage persistence per language and settings.
  - runCode() triggers Judge0 calls and updates output/error state.
- Execution API wrapper: src/lib/judge0.ts
  - POST /submissions?base64_encoded=false&wait=true
  - Normalizes stdout, stderr, compile_output.
- Snippet flows: convex/snippets.ts
  - createSnippet, deleteSnippet, addComment, deleteComment, starSnippet.
  - getSnippets, getSnippetById, getComments, isSnippetStarred, getSnippetStarCount, getStarredSnippets.
- Execution history and analytics: convex/codeExecutions.ts
  - saveExecution, getUserExecutions (paginated), getUserStats (aggregations).
- User sync: convex/http.ts and convex/users.ts
  - /clerk-webhook verifies Svix signatures and syncs user.
  - Fallback in snippets.createSnippet auto-creates user if webhook is delayed.

2.3 Data flow (step-by-step)

Flow A: Run code
1) User edits code in Monaco (EditorPanel.tsx).
2) RunButton triggers useCodeEditorStore.runCode().
3) runCode() maps language to Judge0 ID (LANGUAGE_IDS).
4) executeCode() sends POST to Judge0; response includes stdout/stderr/compile_output.
5) Store updates output or error; OutputPanel renders result.
6) If authenticated, RunButton saves execution via api.codeExecutions.saveExecution.

Flow B: Create snippet
1) User opens ShareSnippetDialog, submits title.
2) getCode() reads editor content; api.snippets.createSnippet is called.
3) Convex verifies user identity; creates user if missing.
4) Snippet stored in snippets table; UI reflects new snippet.

Flow C: View snippet + comment
1) Snippet detail page loads snippet and comments via useQuery.
2) Comments list renders CommentContent, parsing code fences.
3) Add comment triggers addComment mutation; server checks identity and author.
4) UI re-renders via reactive query.

2.4 Scalability considerations
- Snippets page currently loads all snippets and filters client-side; should move to server-side filtering and pagination.
- Convex indexes exist on users, codeExecutions, snippetComments, stars for common access patterns.
- Execution results and output are stored as strings; size limits should be enforced for long outputs.

2.5 Trade-offs
- Convex and Clerk accelerate development but introduce vendor lock-in.
- Judge0 removes runtime maintenance but adds external dependency and latency.
- Client-side filtering is simple but not scalable for large datasets.

3) DATABASE DESIGN

3.1 Schema design (Convex)
- users: { userId, email, name } with index by_user_id
- codeExecutions: { userId, language, code, output?, error? } with index by_user_id
- snippets: { userId, title, language, code, userName } with index by_user_id
- snippetComments: { snippetId, userId, userName, content } with index by_snippet_id
- stars: { userId, snippetId } with indexes by_user_id, by_snippet_id, by_user_id_and_snippet_id

3.2 Relationships
- users -> snippets (one-to-many)
- users -> codeExecutions (one-to-many)
- snippets -> snippetComments (one-to-many)
- users <-> snippets via stars (many-to-many)

3.3 Indexing and query optimization
- by_user_id on users and codeExecutions for profile queries.
- by_snippet_id on comments and stars for detail page metrics.
- by_user_id_and_snippet_id for quick isSnippetStarred checks.

3.4 Example queries
- Fetch user executions (latest first):
  - Query codeExecutions with index by_user_id and order desc.
- Fetch snippet comments: by_snippet_id index.
- Check star status: by_user_id_and_snippet_id index.

4) BACKEND DEEP DIVE

4.1 API design
- Convex query/mutation API (not REST/GraphQL).
- Queries are reactive and return live updates to clients.

4.2 Key mutations (request/response examples)

saveExecution
- Request: { language: "javascript", code: "console.log(1)", output: "1" }
- Response: void (success)

createSnippet
- Request: { title: "Two Sum", language: "javascript", code: "..." }
- Response: snippetId

addComment
- Request: { snippetId: "id", content: "Great solution" }
- Response: commentId

starSnippet
- Request: { snippetId: "id" }
- Response: void (toggles star)

4.3 Authentication and authorization
- Clerk provides identity; Convex reads it via ctx.auth.getUserIdentity().
- All write mutations require identity; deletion checks ownership.

4.4 Middleware
- Next.js middleware uses Clerk to protect routes.
- Convex HTTP action verifies Svix signatures for webhook requests.

4.5 Error handling
- Convex mutations throw errors on auth failure or missing records.
- Client catches and displays toast errors in several UI flows.

4.6 Security practices
- Auth guard on all writes.
- Webhook signature verification with CLERK_WEBHOOK_SECRET.
- Additional hardening needed: rate limiting, output size caps, comment sanitization.

5) FRONTEND DEEP DIVE

5.1 Component architecture
- App Router pages under src/app.
- Feature folders: (root), snippets, profile, privacy, terms, support.
- Shared components in src/components.

5.2 State management
- Zustand store in src/store/useCodeEditorStore.ts for editor state and execution output.
- Convex hooks (useQuery, useMutation, usePaginatedQuery) for data.

5.3 Routing
- /: editor page
- /snippets: snippet list
- /snippets/[id]: snippet detail
- /profile: user profile and history
- /privacy, /terms, /support: static legal/support pages

5.4 Performance optimization
- Monaco is client-only with useMounted to avoid hydration mismatch.
- Skeleton components for loading states.
- Lazy UI updates via Convex reactive queries.

5.5 API calls
- Judge0 via fetch in src/lib/judge0.ts.
- Convex queries/mutations via convex/react hooks.

5.6 UI/UX decisions
- Editor + output side-by-side for fast feedback.
- Snippet cards show language and preview; comments support code fences.
- Profile dashboard emphasizes recent activity and language usage.

6) FULL FLOW (END-TO-END)

User runs code
1) User types code in Monaco.
2) Clicks Run -> Judge0 execution.
3) Output renders; execution is saved to Convex if signed in.
4) Profile page shows updated stats and history.

13) INTERVIEW QUESTIONS & ANSWERS 

1. Why choose Convex instead of a REST backend?
Answer: Convex provides reactive queries, built-in auth enforcement, and rapid iteration without managing servers.

2. How does code execution work end-to-end?
Answer: Editor state -> runCode -> Judge0 POST -> stdout/stderr -> UI output -> optional saveExecution mutation.

3. How do you secure mutations?
Answer: Every write uses ctx.auth.getUserIdentity(); ownership checks on deletes.

4. How do you scale snippet browsing?
Answer: Replace client-side filtering with server-side filters and pagination; add indexes.

5. What happens if Clerk webhook fails?
Answer: createSnippet fallback creates the user if missing.

6. How do you handle unsupported languages?
Answer: runCode checks LANGUAGE_IDS; returns a friendly error if missing.

7. Where is execution history stored and how is it used?
Answer: codeExecutions table; queried for profile and stats aggregation.

8. How would you add rate limiting?
Answer: Track recent executions per user in Convex and reject over quota.

9. How are comments rendered safely?
Answer: Currently raw; should sanitize on server or before rendering.

10. How is state shared between components?
Answer: Zustand for editor state; Convex hooks for data.

11. What are the biggest external dependencies?
Answer: Clerk for auth, Convex for data, Judge0 for execution.

12. How is authentication applied to routes?
Answer: Clerk middleware guards all routes and Convex uses identity checks.

13. How would you reduce Judge0 latency?
Answer: Batch requests or add a queue; consider pre-warming or a dedicated instance.

14. How would you add snippet search?
Answer: Add Convex query with filters, pagination, and indexes or a search service.

15. How do you handle output size?
Answer: Truncate output on client and enforce max size on server.

16. What is the data model for stars?
Answer: stars table with userId and snippetId; composite index for fast lookup.

17. How do you ensure comment deletion is safe?
Answer: Validate identity and compare comment.userId to identity.subject.

18. How does the profile page load history?
Answer: usePaginatedQuery on getUserExecutions; loadMore for pagination.

19. How would you test the execution flow?
Answer: Unit tests for Judge0 wrapper + Playwright UI tests for run flow.

20. Where are environment variables used?
Answer: Convex URL in client provider, Judge0 URL in judge0.ts, webhook secret in http.ts.

21. What are the main performance risks?
Answer: client-side filtering and large execution outputs.

22. How do you handle hydration issues?
Answer: useMounted and client-only rendering for Monaco.

23. Why is Convex suitable for this use case?
Answer: Real-time updates for snippets/comments and easy auth integration.

24. How would you implement organizations?
Answer: Add org table, org membership, snippet visibility, and RBAC checks.

25. What would you improve first?
Answer: Server-side snippet search, rate limiting, and testing coverage.

14) ELEVATOR PITCH 
Codecraft is a Next.js App Router platform that lets developers write and run code in a Monaco editor, execute it remotely via Judge0, and share snippets with comments and stars. Clerk handles authentication and Convex provides a reactive data layer and serverless backend. The result is a fast, zero-setup coding playground with community features and personal execution analytics.
